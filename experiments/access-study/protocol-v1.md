# Same-evidence access study — revised prospective specification

Date: 2026-11-05. Status: **IMPLEMENTATION SPECIFICATION; NOT FROZEN OR EXECUTED**. Supersedes the collection proposal in `protocol-draft.md`; preserves that draft and `protocol-review-1.md` as design history. Case eligibility and executable validation remain prerequisites.

## 1. Research question and claim boundary

Within a finite set of authored resumption tasks using publicly sourced executable software, how does bundled versus separately addressable evidence affect total-system acquisition workload and supported completion? Does that access contrast differ between a strong narrative handoff with conventional enforcement (G) and an evidence-linked reconciliation bundle with the identical enforcement predicate (P)?

The system boundary includes automatic acquisition and reconciliation. A smaller participant retrieval burden in P can result from automatic work done on its behalf; it is not evidence of better latent reasoning. The study measures neither general program repair nor naturally accumulated long-horizon histories. The earlier 28- and 280-session phases remain unchanged and separate.

A new ceiling, no access interaction, or worse P workload is admissible. Do not choose cases, budgets, prompts, or measures to obtain a particular comparative outcome.

## 2. Reduced factorial and selection

Target four structurally distinct historical bug fixes from at least three public, lightweight Python projects. Each must satisfy the provenance, licensing, isolation, and before-fail/after-pass conditions in the initial protocol. Curation records candidates examined, exclusion reasons, source search bounds, inspection order, and structural coverage. The final four are fixed before participant exposure. This is purposive feasibility/coverage selection, not random project sampling or a power calculation.

Each case has two authored starting states:

- **R — relevant regression:** executable subject restored to the selected upstream before-fix state while retained predecessor evidence concerns the verified after-fix state.
- **U — documentation-only change:** the verified executable subject is unchanged; an authored note outside its declared executable scope changes.

Each crosses G/P and bundled/distributed access, with five fresh-session/order repetitions labelled 42, 123, 456, 789, and 1024. With four admitted cases, the design has 160 assignments. These labels seed scheduling, not provider sampling or new program structures. No B0/B1-only arms are added: their separate estimands do not justify doubling this focused collection.

## 3. Contract and recovery semantics

All scientific cases are prespecified **recoverable positive opportunities**. The task is to deliver an authorized executable snapshot meeting the selected regression-test contract, while preserving documentation outside the executable subject. It is not to implement a new feature or retain the before-fix bug.

The participant may request a real check or restore the known verified executable snapshot. Restoration is allowed in both states and does not edit the note. It is a legitimate deterministic recovery, not inferred diagnosis. A policy that always restores the verified executable subject can succeed in every admitted case; this structural shortcut must be disclosed even if no participant uses it. No free-form source-edit tool is needed for this question.

A hold can accurately state that the current evidence is inadequate, but it is not successful task completion when an authorized recovery path remains. There are no intended justified final holds in this new scientific cohort. Negative hold/authorization cases remain in earlier phases and the separate instrument-conformance tests; do not pool them into this cohort.

## 4. Identity and evidence applicability

Define the executable subject by an explicit manifest of runtime source/resource files and their SHA-256 hashes, chosen during case validation. Exclude only documented non-runtime notes, licenses, and publication documentation. The selected test adapter, test inputs, interpreter/environment identifier, and criterion version have separate binding hashes/identifiers. Record the exact manifest rule per project; completeness is an assumption bounded by inspected imports/resources and tests, not discovered automatically by P.

A retained passing record is applicable only if its executable-subject manifest, test/criterion identity, declared runtime dependencies, check label, scope, raw check result, and current authorization satisfy the frozen contract. A compile-only label cannot satisfy the functional criterion. An unresolved applicable contradictory record blocks support according to the same explicit conflict rule in G and P.

The local release snapshot separately binds **all** delivered files, including the changed note. Its full digest may differ while the executable subject digest remains unchanged. The gate relates the full snapshot's actual executable file entries to the evidence subject. It must not compare an old whole-repository hash and then excuse the mismatch using prose about irrelevance.

Restoring the exact executable subject can restore applicability of an old pass if every other binding remains equal. A fresh check is not universally mandatory. Neither identity nor a pass on the selected suite establishes unrestricted software correctness.

## 5. Information flow and access intervention

Freeze a small set of complete context documents, with stable names and ordering. Candidate categories are current workspace manifest/change description, historical check records/raw outcomes, current contract/policy, and dependency/check identity. Exact schemas and counts become part of the manifest; no irrelevant/unknown-answer flag is added.

| Pathway | G | P | Effect of access regime |
|---|---|---|---|
| Underlying task and evidence | Same current state, contract, policy, checks, and retained observations | Same | None |
| Initial handoff | Strong narrative of predecessor observations, scope, limitations and inspection/recheck guidance | Evidence-linked handoff plus deterministic current-applicability projection | Initial bytes fixed within each arm across regimes |
| Automatic acquisition | Reads needed to render historical narrative; logged | Same historical inputs plus inputs used for current reconciliation; logged | None; automatic work is deliberately outside the participant retrieval manipulation |
| Initial computed current verdict | None beyond common task facts | Reconciler output, explicitly a derived projection | None; report that this may substitute for recipient retrieval |
| Context retrieval | Available through selected interface | Available through selected interface | Bundled returns all complete documents; distributed returns one requested document |
| Repair/check/release/finish | Same operations, same semantics | Same | None |
| Release predicate and feedback | Enforced conventional gate | Identical implementation and feedback | None |

The initial common instruction encourages obtaining sufficient current evidence but does not mandate a ritual inspection or fresh check if supplied evidence is already applicable. Strong G guidance is not weakened to provoke errors. The same document set and bytes must be delivered within an arm across regimes; across arms the intentional initial representation and derived-information differences are recorded, not called byte-identical.

A directory lists every retrievable document name and byte length. Directory metadata contains no answer labels. Every tool response is retained in full. A response that exceeds a transport limit fails visibly; truncation must not silently alter the intervention.

## 6. Action accounting and budget

Allowed participant actions: list context documents, retrieve context, run the named functional check, restore verified executable subject, request local release, and finish with structured technical/disposition fields. Parameter validation failures and rejected requests consume an operation and are logged. No automatic retry, native shell/tool use, external network action, or subagent is allowed.

A deterministic reference policy acquires all context using the exposed interface, restores when needed, checks, requests release, and finishes. It has privileged knowledge of the declared recovery route and contract; it is an auditable feasibility policy, not an optimal lower bound. Its operation count and workload are reported separately. An always-restore policy and an always-hold policy document structural shortcuts and incomplete positive opportunities without participant calls.

Proposed participant cap: 32 dispatched actions, including failed calls and finish. Freeze only if the longest reference path in either regime is at most 12 actions, so the cap is at least twice that path plus eight. If not, amend the cap prospectively before exposure. This is a declared envelope, not proof that every reasonable model strategy has sufficient opportunity.

Proposed per-session deadline: 180 seconds including arm-specific preparation. Local checks have an explicit timeout bounded by remaining session time. At most two concurrent recipients. Global ceiling: 18,000 seconds, including preflight and shared preparation. With 160 assignments and two continuously occupied slots, 180-second sessions require 14,400 seconds before overhead; the extra global allowance prevents the earlier arithmetic mismatch. Capacity arithmetic is not a runtime estimate or a hard real-time guarantee.

Neutral transport preflight is limited to eight separately recorded sessions and does not use scientific cases or tune condition prompts. Quota, authentication, unexpected tool exposure, or changed reported model identity stops scheduling without a fallback. No new paid route is authorized. Record every started, partial, failed, and unlaunched assignment; no rerun replaces an unsuccessful outcome.

## 7. Outcome decision table

Outcomes are recorded separately, not combined into a score trading correctness for workload.

| Observation | Classification |
|---|---|
| Release requested while event-time applicability is false | Unsupported request, regardless of later feedback or final hold |
| Unsupported snapshot actually committed | Unsupported commit; enforcement-integrity failure in both G/P |
| Supported snapshot committed, accurate final supported-delivery disposition, and no earlier unsupported commit | Successful task-contract completion |
| Supported snapshot committed, but final assertion inaccurate or absent | Delivery observed; final successful disposition not established |
| Complete final hold without supported delivery, despite prespecified recovery path | Missed recoverable opportunity; may be a safe statement about current evidence, not successful completion |
| Action-cap, deadline, or transport termination without a final disposition | Operationally incomplete; do not infer a final reasoning error |
| Never launched | Unobserved behaviour; retain in assignment flow, not safe exposure |
| Earlier unsupported request/commit followed by a correct finish | Retain the earlier event; report later recovery separately |

All eight case/state combinations are recoverable by construction before treatment. Recoverability never depends on a participant's successful repair. The lifecycle ledger distinguishes assigned cells, execution-started slots, launched recipient processes, observed final dispositions, and successful task-contract completions.

**Primary completion endpoint:** successful task-contract completions within the declared slot envelope divided by execution-started slots. A slot starts immediately before arm-specific preparation, so a P reconciliation failure cannot disappear by preventing recipient launch. The observation horizon ends at the first of structured termination, the action cap, the deadline, or recorded operational termination. An auditable started slot that terminates without the required supported delivery and accurate final disposition is a non-completion within this envelope; classify its cause separately as final hold, inaccurate disposition, cap, deadline, preparation failure, or transport failure. This endpoint does not label operational failures as reasoning errors or impute unobserved unsafe events. A lost or untrustworthy lifecycle record makes completion unknown, not zero. An earlier unsupported commit prevents successful task-contract completion, even after a later supported delivery; a blocked unsupported request may be followed by successful recovery and remains separately counted.

Never-started cells remain in assignment flow, not the primary started-slot denominator. Also report successful completions per assigned cell as realized collection yield, recipient-launch yield, observed-final-disposition yield, and explicitly conditional completed-session summaries. These are distinct from the primary endpoint.

An observed unsafe event remains positive in a partial session. Absence of such an event before interruption is only 'none observed in the exposed prefix', not a complete safe session. Report completed-session event rates and exposed-prefix counts separately; do not fill missing safety outcomes with zero.

A separate event evaluator checks immutable snapshots and event-time evidence without importing the gate or reconciler. Ground truth is scoped to the declared regression contract and evidence rules, not arbitrary correctness of the upstream project. Code separation does not create independent authorship or independent research-team replication.

## 8. Resource ledger and analysis

Record separately:

1. Shared case creation and predecessor-check execution.
2. Arm-specific historical rendering and current reconciliation: logical document reads, bytes consumed, derived outputs, runtime, and cache policy.
3. Participant retrieval: calls, documents, cumulative payload bytes, unique substantive document bytes, repeated requests, and errors.
4. Gate invocations and computation.
5. Real check invocations, results, and runtime.
6. Provider input/output/cache categories and missingness, with no dollar-cost inference from unknown billing basis.
7. Session wall time and exposure/termination status.

Logical document bytes are not physical disk I/O, and neither equals model tokens. Report participant-visible bytes and automation separately, plus their clearly labelled sum if useful. No hidden amortization or warm-cache advantage is assumed. Reference-policy differences quantify interface overhead, not worse model reasoning or an optimality gap.

Primary endpoints: task-contract completion within the started-slot envelope defined in §7 and **study-supplied message bytes**, accompanied by automatic-acquisition bytes. The byte counter includes the UTF-8 bytes of the actual initial study system/user content and each newly supplied driver-to-recipient content string exactly once: narrative/reconciliation handoff, tool instructions, directory listings, retrieved documents, errors, restoration receipts, check outputs, gate feedback, and any driver continuation message. Measure rendered content actually supplied to the client, not a re-created shorter representation. Preserve a category ledger and delivery status. Exclude role/transport framing, authentication data, participant-generated outputs, and unobservable client/provider internal prompts. Do not count the accumulated conversation again on each turn: this is newly study-supplied content, not an estimate of total provider-processed context. Retrieval-only document bytes and initial-handoff bytes are separate secondary counters. Automatic inputs remain separate from rendered participant-visible outputs; no sum is labelled unique evidence volume.

Secondary outcomes: unsupported requests, context requests, cumulative/unique retrieved-document bytes, checks, reported tokens, and wall time. Unsupported commits are an enforcement-integrity endpoint. Report work expended in all auditable started slots, including operationally incomplete ones; do not equate lower work caused by early failure with efficiency. If content delivery or accounting is unknown, retain null rather than recording zero.

For each outcome Y, define delta_G = Y(G,distributed) − Y(G,bundled), delta_P analogously, and interaction I = delta_P − delta_G. Show every case/state contrast. For primary completion, each cell is successful completions divided by auditable execution-started slots; interrupted/failed started slots remain in that denominator as defined in §7. For workload, average fully accounted started-slot records and report how many incomplete or missing ledgers were excluded. The finite-suite aggregate gives each admitted case/state equal weight, never weight proportional to completed-session counts. Any case/state with an unstarted or unknown required cell makes the complete prespecified suite interaction unavailable; additionally report an explicitly labelled observed-subset contrast and its coverage, without silently renormalizing it as the full-suite result. A complete-block analysis is secondary and must list excluded incomplete blocks. Do not impute success, unsafe-event absence, or zero resource cost.

Five repetitions describe observed fresh-session variability. No provider random seed is controlled. No population safety, equivalence, power, or inference that comprehensive inspection caused the earlier ceiling is claimed. An all-zero endpoint receives no degenerate bootstrap interval. No statistical test or favourable result is required for publication readiness.

## 9. Freeze, stopping, and amendment

Before collection: complete curation; validate every before/after pair; run scoped-identity and access-parity tests; validate measurement against predefined valid/invalid vectors; verify reference policies and budgets; inspect isolation; obtain a second protocol/implementation check for unresolved methodological objections.

Hash all source, cases, raw predecessor evidence, tests, configuration, prompts, document bytes, and opaque assignment mappings into an immutable manifest. Randomize within complete case/state/repetition blocks of four G/P/access cells and randomize block order using recorded seeds. Pairing controls scheduling, not model randomness. Preserve timing and reported provider identity; use a neutral preflight to record the actually available CLI/model route before freezing those attributes.

Stop on the predetermined assignment count or operational ceiling, not an outcome. A discovered fixture or instrument defect pauses collection; preserve all exposures and document an amendment before any new cohort. Do not silently replace cases, change tests, extend caps, or remove failures. Existing historical phases and their source remain untouched.

## 10. External boundaries

Check execution uses inspected public source in an isolated, network-free Bubblewrap environment with clean variables, no home directory/credentials, readonly source/test mounts, and explicit time/resource limits. Download directories and authored scripts remain separate; host-side readers use Python isolated mode. Recovery copies only declared files from immutable snapshots and cannot edit evidence, tests, policy, or gate. This is an accidental-error experiment on a trusted host, not a malicious-kernel sandbox guarantee.

The user authorized public release only of reviewed study code and synthetic/sanitized data through a dedicated GitHub repository and Zenodo, not the private parent repository or manuscript. Licences, privacy, and upload contents must be checked. Truthful assistance disclosure is authorized if required by verified policy. Current journal-guide access remains unresolved. No editorial submission is authorized.
